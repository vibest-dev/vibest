# Effect

1. Following Effect, code takes every dependency (`FileSystem`, `Path`, `ChildProcessSpawner`, clients, other services) from the service graph it runs in, resolved when its layer or the composition is built and closed over. Nothing builds its own platform layer or a service instance inside a method or at module level (for example a plugin providing `NodeFileSystem.layer` itself).
2. A module follows OpenCode's shape: it exports itself as a namespace (`export * as Inbox from "./inbox.ts"`) holding `Service` (the `Context.Service` class), `Interface` (its shape), `layer` (its production layer), `node` and, when it takes options, `configured(options)`. The effect that builds the service is `make` (a value, or a function when it takes arguments); a test double is `testLayer`, next to the service when it has no test-only dependencies. A second service in the same module (a host input such as `Identity.HostFacts`) keeps its own class with a `<name>Node` beside it, as OpenCode's `Shell.Daemon` and `daemonNode`. Do not add `live`, `Live` or plural `layers` names. `node = LayerNode.make({ service, layer, deps })` places the service in the service graph; its `deps` list the node of every service the layer reads (the type check refuses a missing one). Wire a service through `deps` and replacements ([architecture §5](../../docs/design/architecture.md#5-service-composition)), not with `Layer.provide` chains at a root; a node's own layer may compose layers inside it (`server/src/server.ts` builds the RPC server that way).
3. A value the host must supply (the daemon's identity and shutdown signal, the host environment) is a `Context.Service` with no default, so a missing wire fails to compile, and its node is `LayerNode.unbound(Service)`, so a graph that reaches it without a replacement fails when it is compiled. This applies to the vibestd service graph; the CLI has no `LayerNode` graph (it may not import core), so its host input is a `Context.Service` with no default provided directly at the CLI entry, as OpenCode provides its CLI services. Use `Context.Reference` only when its default is correct in production.
4. A service method's requirements are `never`: resolve dependencies when its layer or the composition is built and close over them. Do not hand `Scope`, `FileSystem` or another service to callers through a method's type, and do not capture a context to `provideContext` it back into a method.
5. Failures at the platform boundary are `Schema.TaggedError`s (`LockFailed`, `DatabaseOpenFailed`, `SchemaMismatch`), never a plain `Error` or `unknown`; new `Effect.tryPromise` and `Effect.try` calls pass a `catch` that maps to one.
6. A public effect is `Effect.fn("<Module>.<name>")`, so its span and stack name it. A new log line puts ids and the cause in structured fields (`Effect.logWarning("message", { "session.id": id, cause })`), not spliced into the text. Convert existing methods when you touch them; there is no sweep.
7. Down by call, across by fact. A service calls the services below it; it learns about another domain's change by a fact, registering its reaction with `reactor.on([Definition], handle)` (`Reactor.make`) in its own layer, never by being called back by that domain.
8. A durable change is its rows plus its facts in one commit. Services change durable state only through `Db`; inside `packages/core/src/database/` a write runs in `bus.transaction` and records each fact with `bus.publish(Definition, …)`, and the Bus delivers the facts once the transaction commits. Fact definitions live in `@vibest/schema/event`. SQL lives only under `packages/core/src/database/`.
9. No dependency bags and no back-fill: a function does not take a record of services (`{ db, plugins, fs, … }`), a module does not fill a `let` with a dependency after it is built, and nothing `import()`s a module lazily to break a cycle. Extract a smaller service, or react to a fact (rule 7).
10. Each piece of in-memory state has one owner service. A background fiber belongs to a layer scope (`Effect.forkScoped`, `FiberSet`, `FiberMap`); loops run only as [no-background-polling.md](no-background-polling.md) allows.
11. Transport (the RPC handlers in `packages/server/src/handlers/` and `http.ts`) holds no domain logic and no lock: it resolves the caller, calls a service and maps the answer.
12. Effect code does not leave Effect to run Effect: no `Effect.runSync`, `runFork` or `runPromise` inside a service or a handler.

13. `catchCause` (and `Stream.catchCause`) belongs only at a supervision point: the Reactor's handler wrapper, the plugin supervisor and host, a runtime's event pump. It lets a pure interrupt through (`Cause.hasInterruptsOnly(cause) ? Effect.failCause(cause) : …`), so cancelling the caller still cancels the work. Elsewhere catch the tagged failures you expect (`catchTag`, `catchTags`).
14. A test compiles its service graph in the package of the module under test: `LayerNode.compile(node, { replacements: [...base, ...replacements] })` from that package's own `test/`, with fakes for the services below it, not another package's composition root.

Status: rules 1, 7 and 8 hold on main. Exceptions today:

- Rules 2 and 6: these service modules still export a bare `Context.Service` class instead of a namespace (core `bus.ts`, `database/db.ts`, `plugin/service.ts` with `pluginsNode` in `plugin.ts`, `plugin/sources.ts`, `session/archive.ts`, `delivery.ts`, `entry.ts`, `executions.ts`, `exits.ts`, `live.ts`, `locks.ts`, `move.ts`, `placement.ts`, `reconcile.ts`, `restart.ts`, `spawn.ts`, `subscriptions/service.ts`).
- Rule 3: `Builtins` (`plugin.ts`) and `UserPlatform` (`system-prompt.ts`) are `Context.Reference`s whose default is right only in tests.
- Rule 4: `MachineTransport` (`server/src/machine/machines.ts`) and `ShutdownHost.onSignals` (`server/src/shutdown-deadline.ts`) require `Scope` in their type; `plugin/sources.ts` captures `Effect.context` for `Effect.runFork` in watch callbacks, and `server/src/shutdown-deadline.ts` does the same with `Effect.runForkWith`.
- Rule 5: `MachineTransport` fails with a plain `Error`, which `platform-bun/src/bun.ts` builds in its transport; `SystemPromptDirUnsafe` (`system-prompt.ts`) and `AgentOwnLimit` (`session/placement.ts`) are `Data.TaggedError`s, not `Schema.TaggedError`s.
- Rule 9: `server/src/listing.ts` (`sessionListing`) takes a dependency bag (`{ db, sessions, runtimes }`).
- Rule 10: `effect/bounded.ts` detaches the interrupt of a late fiber (`Effect.forkDetach`).
- Rule 11: `server/src/handlers/session.ts` keeps a per-session lock (`seenLocked`).
- Rule 12: `database/session-statements.ts` runs after-commit effects with `Effect.runSync`; `plugin/sources.ts` and `server/src/shutdown-deadline.ts` fork from callbacks (rule 4).
- Rule 13: `session/restart.ts`, `session/placement.ts` (`launch`), `runtimes.ts` (`runtimesHere`) and `server/src/machine/machines.ts` (`ensure`) catch every cause, pure interrupts included, outside a supervision point; the supervision wrappers `reactor.ts` (`logFailure`) and `plugin/supervisor.ts` (the first activation) end a pure interrupt quietly instead of passing it on, and `session/delivery.ts` (`failed`) returns on one.
- Rule 14: `core/test/lib/session.ts` composes server's `services` root with server's `Identity`, `Shutdown`, `MachineTransport` and `UpdateCheck`, and server behaviour (handlers, machines, the daemon) is tested under `packages/cli/test`.
