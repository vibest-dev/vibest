# Guard and Memory

1. Under the projects directory the guard allows only the session's own project folder, `VIBEST_PROJECT_DIR` (`projects/<project id>`): every agent reads and writes it with its own file tools, and nothing else there. It does not infer anything from path shapes: a project folder is named by its project id.
2. The coordinator writes files only inside `VIBEST_PROJECT_DIR`; its pre-tool hook refuses every other file edit. A subagent gets the folder without permission prompts (Claude: `--add-dir` and `Read`/`Edit` allow rules limited to it).
3. Every new path that opens a terminal passes the session key, so `VIBEST_PROJECT_DIR` is set. Its subfolders are fixed: `docs/`, `memories/`, `artifacts/`.
4. The guard and memory will be redesigned. Until then, do not extend guard rules ad hoc.
5. The guard checks what a tool call says; it is not a sandbox. A call is allowed unless a rule names it. A shell command can reach a path or program no rule recognizes, and a hook that times out lets the call through (the harness decides): the harness's own sandbox is the boundary. Which vibest commands an agent may run is vibest's own check where they run (`cli.ts` `userOnly`, `server.ts` `ACCESS`), not the guard's. Hook input the guard cannot read refuses the call: `vibest integration guard` exits non-zero on any failure, a missing `VIBEST_AGENT` included, and the hook script turns that into a refusal.
6. Every agent: no herdr control (`agent`, `pane`, `tab`, `workspace`, `worktree`, `server`, `session`), and a session runs no herdr at all (the coordinator may read herdr's help); no `vibest` with `VIBEST_SESSION_ID` or `VIBEST_AGENT` assigned, exported, unset or cleared anywhere in the command (a bare `VIBEST_AGENT=` changes the exported value too), since vibest's caller identity comes from them; no `vibest integration stop` or `prompt`, which are the harness's hooks. The coordinator also starts no harness CLI (it would inherit the coordinator's identity) and runs no `gh alias|extension|config|auth`.
7. Shell commands are split best effort, not as a shell: at unquoted `|`, `&`, `;`, `(`, `)` and newlines, with redirection targets, `#` comments and here-document bodies left out, the commands in `$(…)` and backquotes added (a quoted `)` inside `$(…)` ends it early), and wrappers (`env`, `sudo`, `xargs`, …), `sh -c` and `eval` followed. Variables, aliases and functions are not expanded. For a session, each word with `/`, `~` or `.vibest` is then judged as a path from the call's cwd: a search program (`rg`, `grep`, `find`, …) given a directory above the projects directory, vibest's home itself (a later `cd` would make relative paths land inside), a glob or variable in a `.vibest` word, and a `.vibest/projects` word outside the own folder (it may be relative to an earlier `cd`) are refused. This catches a project named directly, which is what an honest mistake looks like.
8. Paths are read as Cursor's tools read them: a `file://` URL as its path (one that does not parse, or that Bun decodes to an empty path, is refused), a leading `~` as `HOME`, a relative path under the cwd. Each path is judged as the system follows it (segment by segment, each existing symlink before a later `..`) and as a tool that normalizes it first (Cursor's do). A dangling symlink as the last segment counts as its target, since a write creates it; a symlink that refers to itself or cannot be read is refused. A path that goes on past a regular file (`ENOTDIR`) is judged by its text alone. The cwd is the hook's `cwd`, else its only workspace root (Cursor may send none), and for a Cursor Shell call its own `tool_input.cwd`, normalized.

Status: in force on main (`packages/core/src/guard.ts`; `VIBEST_PROJECT_DIR` is set by `vibestEnv` in `packages/core/src/sessions.ts` and, for the coordinator, `coordinatorCommand` in `packages/core/src/launch.ts`).
