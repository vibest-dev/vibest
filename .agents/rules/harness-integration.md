# Harness Integration

1. Results and messages never come from a pane's screen. No screen text is pushed to an agent; `vibest peek` is only for an agent or user to inspect a terminal when needed.
2. Claude is integrated through its native hooks module only (`turn.complete`, `prompt.submit`, `tool.call`): no `settings.json` and no classic hooks; its only `--settings` is inline and grants the project folder and session scratchpad (`{"permissions":{"additionalDirectories":[<projectDir>,<scratchDir>]}}`), with no hooks or deny rules. The plugin loads at launch with `--plugin-dir` and is never installed (see [user-file-mutation-safety.md](user-file-mutation-safety.md)).
3. All four builtin harnesses (`claude`, `pi`, `cursor`, `agy`) reach `vibestd` directly over the Unix socket (`/api/hook/*` and `/api/inbox/*`, currently `vibest-http.sock` on `main` and unifying onto `vibest.sock` in [http-api-and-naming.md](http-api-and-naming.md)). No harness invokes a `vibest integration` CLI subcommand. Claude uses `$.http.fetch` with literal `$.env.get` names; Cursor and agy use `curl --unix-socket`; Pi talks in-process over the socket.
4. A delivered message shows in the harness UI; its full text goes with it as context. Nothing is injected into the system prompt. vibestd sends `detail` (one entry per message: `{ sender, message }`, `message` the unwrapped text) next to `content`. `sender` is `{ agent, title, session }`, `{ agent, title, session, machine }` (an agent on another machine), `{ address }` (`machine/id` when the peer sent no agent), `"vibest"`, or `"user"`. The sender record (`session`, `agent`, `title`) is made once on the machine where the message starts and travels unchanged on every path (local send, forwarded `Send`, outbox relay); the first machine that receives it from another adds `machine`, its own name for the machine it came from, and later hops keep it. Routing (recipient, hop) never rewrites it. A send with no session is shown verbatim. vibestd does not trim or format. Each integration formats `detail` itself by iterating it.
   - Claude and Pi: one two-line block per entry. An agent is `Message from @<Agent>` (the definition id, first letter capital) `· <session title> (<first 8 of the session id>)`, then the first line, about 120 characters. A notice is `Message from Vibest` (no @). A send with no session is `Message from You`. A remote agent is `Message from @<Agent> · <title> (<machine>/<first 8>)` when the peer sent the agent and title, and `Message from @<machine> · (<machine>/<first 8>)` when it did not.
   - An execution's completed or failed is what the harness reported (a normal end or an error), never parsed from the agent's text.
5. No recovery commands for the user to type (no `/vibest-reattach`). Delivery recovers by itself: a pulling integration takes its next batch whenever it is idle, and a batch it never took up is settled by the execution's confirmation timeout.
6. Per-harness differences (launch arguments, resume, `canResume`, models, subscription reading, the guard's answer shape) live in the harness definition (`HarnessDefinition` in `@vibest/plugin`), which a plugin adds; the builtin ones are in `packages/plugin-harnesses`. Core and the CLI never branch on a harness id; they read definition fields from the `Harnesses` registry.

Status: in force on `main` (PR #655 removed `vibest integration`).
