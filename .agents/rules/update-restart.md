# Update and Restart

1. No hot reload.
2. `vibest update` hands vibestd off to the new version: it plans to keep running, hand off or restart, and says why. The user runs it, or the project's main agent from its own shell (`--yes`: that shell has no terminal); no other agent may. When vibestd is replaced instead of handed off, only the user's no keeps the update successful: any other replacement that did not happen is said at once and fails the update (non-zero) after the remaining steps. Nothing is retried. Before it installs anything it fetches the new version aside and has it open the database (`vibest daemon import-check`); when it cannot, the update installs nothing, leaves vibestd running and says why and what to do, so an update never leaves a CLI that cannot talk to the vibestd that runs.
3. Then it asks once to restart every agent still on the old integration. Yes restarts them in place (see [runtime-boundary.md](runtime-boundary.md) 4) with the same vibest session and harness conversation; an interrupted execution gets `continue`. vibestd restarts them only after the asking command has exited, since it may run inside one of them (the main agent's shell); it watches that command's pid, whose exit no runtime reports. Subagents restart first, then the main agent, whose continue notice names the subagents restarted with it. An open round stays open across the restart: the continue is another execution of it, and it reports once. The continue instruction is the first line of a main agent's notice and carries no version, so it fits one delivered line and an agent that ran `vibest update` itself does not run it again.
4. `vibest daemon restart` offers the same in-place restart once it has replaced vibestd: both commands ask once and restart through the same code (`restartAgents` in the CLI, `packages/core/src/restart.ts`). There is no other restart command. `vibest daemon restart` runs the same database check first and stops nothing when it fails. Mismatch messages name `vibest update` ([protocol-versioning.md](protocol-versioning.md) 3).
5. An installed version directory is not deleted while a running session uses it.
6. A restart in place: mark the session restarting in its row, SIGTERM to the harness pid only (never its process group; the integration reports the pid with its ready report), then the runtime's optional `run` starts the harness again in the same terminal once its shell is idle. A subagent gets its harness argv on its conversation; vibestd types the main agent's harness command into its shell, prefixed with the identity variables. The pane shell does not keep them, including a pane vibestd opened, because the user types vibest there again after the agent quits. Subagents still get identity from the runtime open. The mark is cleared when the integration reports ready, and however else the restart ends (failed, timed out after 60 s, vibestd stopping), followed by one check of what the mark made the session's checks skip. The harness is the terminal's foreground program, as for a first start: no wrapper loop.
7. Core checks only that `run` exists. An agent whose runtime has no `run`, whose harness never reported its pid, or whose harness has no integration that reports its pid and readiness (Cursor) is not restarted; the update names it and says to restart it by hand. A harness with no integration is never listed as outdated.
8. A usage-limit move takes the same path: only the limited harness ends and the next harness runs in the same terminal.
9. A main agent moved from another terminal (`vibest` there, answered y) ends the same way: SIGTERM to the pid it last reported, its terminal and shell kept, then it starts in the new terminal. While a restart is between its harnesses, that start is refused and nothing is signalled.

Status: decided, planned in the update-restart pipeline plan (`pipeline-update-restart-plan.md` in the project artifacts). 1 to 9 are built on `feat/update-restart-agents-v3` (runtime-herdr implements `run`; core in `packages/core/src/restart.ts`); `vibest daemon restart` offers it too since `feat/multi-install-daemon-restart`.

Known limits:

- A pane with no shell, a remote herdr, another vibest earlier on PATH, and typing in the terminal while `run` types.
- A usage-limit move whose runtime has no `run` or whose harness reported no pid still closes the pane and opens another.
- `run`'s idle check counts `sh` as a shell, so in a main agent's pane typing can start between the harness exit and `exec $SHELL` (the tty keeps the text).
- On the first update from a version before this branch, subagents on the old integration have reported no pid and are listed as "restart it yourself".
- The handoff's database backup is kept per version and never pruned.
- A subagent result the interrupted execution wrote between `executionPromptedAt` and the restart is overwritten by the continue execution.
