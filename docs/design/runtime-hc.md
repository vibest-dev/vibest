# The herdr-core runtime (`hc`)

`packages/runtime-hc` is the builtin runtime plugin of kind `hc`. It drives herdr-core through `effect-hc-sdk`, a client generated from the OpenRPC document `hc schema` prints (pinned in `packages/effect-hc-sdk/schema/`). herdr stays the default runtime: `hc` is chosen with `vibest --runtime hc`, `"runtime": "hc"` in `vibest.json`, or by a subagent whose parent runs in hc.

## Which core

A terminal's vibest id names its core: `<address>@<socket path>`, for example `t3@/run/user/501/herdr-core/default.sock`, so every call on a terminal goes to the core that holds it. A new terminal goes to the core of the terminal it is opened near (a subagent's parent), else to vibestd's own core: `HC_SOCKET`, else `$XDG_RUNTIME_DIR/herdr-core/<session>.sock`, else `${XDG_STATE_HOME:-$HOME/.local/state}/herdr-core/<session>/<session>.sock`, with `<session>` from `HC_SESSION` (default `default`), as hc resolves it. The `socket` key of the core's `config.toml` is not read. vibest never starts a core; `status` asks vibestd's own core and, when none answers, says `offline` and names `hc server start`. Remote machines (`on`, `machine/t7`) are not used yet: every terminal is on its core's own machine.

`vibest` run inside an hc terminal knows it from `HC_TERMINAL_ID` (the terminal's address) and `HC_TERMINAL_SOCKET` (its core), which the core sets in every terminal: it starts the main agent in place, in that terminal on that core, with runtime `hc` (unless `--runtime` names another), as it does in a herdr pane. A `vibest` run outside any terminal with `--runtime hc` opens the main agent's terminal on vibestd's own core.

Each call opens its own connection in plain mode (one JSON-RPC message per line). A core is followed from the first call on one of its terminals: one more connection holds `events.subscribe` filtered by `vibest.runtime=hc`; after a loss it is re-made after 0.5 s, then twice as long each time it fails again, at most 30 s apart; after 8 failures in a row (about 90 s) vibestd stops following that core until the next call on one of its terminals. Each new subscription of a core after its first publishes `reset`, so sessions are checked against what was missed. A `missed` notice drops the connection so the next subscription starts from a fresh snapshot.

## Terminals

- A terminal vibest opens is named `s-<30 hex>` from `VIBEST_SESSION_ID`, else `vbt-<28 hex>`, so `hc ls` shows which session it holds; vibest itself uses its address.
- `open` runs the machine's shell (`keep: true`) and types the argv into it with `terminal.send`, so the shell stays after the program (runtime-boundary rule 4) and `run` types the next program into the same shell. `run` reads the terminal once; when a program still runs in it, it waits for the core's `foreground` event back to the shell (or a fresh snapshot showing it), at most 30 s, without polling. `terminal.send` waits until nobody typed for about 3 s, so each prompt takes at least that long.
- A kept terminal whose program is lost (a signal death, a core crash) gets a shell with the same environment (the runtime-hc test kills the shell with `kill -9` and reads the variable back).
- Exits come from events: `finished`, `removed`, `lost`, and a `foreground` change back to an interactive shell (`sh`, `bash`, `zsh`, `fish`, `dash`, `ksh`, `tcsh`, `nu`, with no script argument) after a program ran. A harness that is itself a shell script would look like a shell; none is.
- `foreground` is the only sign hc 0.1.13 gives that a program typed into a kept shell ended: the pinned `events.subscribe` description does not list it (created, lost, restarted, keep, finished, removed, status, turn, title, labels, size, doc), `status` and `turn` come only from programs that report OSC 7501, and an isolated core sends `foreground` for `sleep 1` going in and coming back to the shell. So the generated SDK and `gen --check` cannot catch a change to it; `packages/runtime-hc/test/notices.test.ts` replays those lines through a fake core socket on every `pnpm test` (exit, `missed` and a closed subscription to `reset`, `run` waiting for the shell), and the live tests and S33 check it against a real core. A program that ends before the core samples the foreground (`true` gives no event at all) is never seen running, so it gets no exit; every harness runs far longer.
- Agent state comes from the harness integrations, carried by the terminal: vibest's Pi integration writes OSC 7501 `working` at a turn's start and `idle` at its end, the core keeps it as the terminal's `status`, and runtime-hc offers `state` from `terminal.get` (`working` and `blocked` as they are; `idle`, `done` and `error` as `idle`; no status as `unknown`) and publishes a `state` event on each `status` event. Without it vibestd showed a main agent as `unknown` all along and a subagent as `idle` in its turn. Readiness and turns still come from the integrations directly.
- A text vibestd sends carries no `caller`, and the core types it byte-identical (no `<hc>` tag), proved by the runtime-hc test.

## Labels: herdr-app's conventions

So vibest agents show in herdr-app too (its `docs/labels.md` and the model of spaces, tabs and terminals):

- Every terminal: `vibest.runtime=hc`; a subagent also `vibest.project=<project id>` and `vibest.session=<session id>` from its environment.
- A main agent's terminal: when vibestd records it (`Project.CoordinatorSession`), it calls `present` with `mainSession` and `projectId`, and runtime-hc labels the terminal `vibest.runtime`, `vibest.project`, `vibest.session`, `herdr.space=<project id>` and `herdr.tab=<main session id>`. Other `present` calls change nothing.
- A subagent opened near another terminal (the main agent's, or a `--peer`'s) is started with `parent` set to it, `outlive_parent` (it keeps running when the main agent's program ends) and `no_notify` (the core types no notes into the parent). Without a terminal to start near, `no_parent`. Delivery, parents and results stay vibest's own.
