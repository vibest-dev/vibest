# The herdr-core runtime (`hc`)

`packages/runtime-herdr-core` is the builtin runtime plugin of kind `hc`. It drives herdr-core through `effect-herdr-core-sdk`, a client generated from the OpenRPC document `hc schema` prints (pinned in `packages/effect-herdr-core-sdk/schema/`). Outside a runtime herdr stays the default. Inside HC, a main agent defaults to HC, and its subagents inherit HC. `vibest --runtime` or a user plugin overrides that default; configuration has no runtime preference.

## Which core

A terminal's vibest id names its core: `<address>@<socket path>`, for example `t3@/run/user/501/herdr-core/default.sock`, so every call on a terminal goes to the core that holds it. A new terminal goes to the core of the terminal it is opened near (a subagent's parent), else to vibestd's own core: `HC_SOCKET`, else `$XDG_RUNTIME_DIR/herdr-core/<session>.sock`, else `${XDG_STATE_HOME:-$HOME/.local/state}/herdr-core/<session>/<session>.sock`, with `<session>` from `HC_SESSION` (default `default`), as hc resolves it. The `socket` key of the core's `config.toml` is not read. vibest never starts a core; `status` asks vibestd's own core and, when none answers, says `offline` and names `hc server start`. Remote machines (`on`, `machine/t7`) are not used yet: every terminal is on its core's own machine.

`vibest` inside an HC terminal is identified by the runtime's optional `caller` capability: the CLI passes only the declared `HC_TERMINAL_ID` and `HC_TERMINAL_SOCKET` values to vibestd. The plugin asks that exact core for `terminal.get`, without `caller` (so no news is acknowledged), returns the terminal's live state and root `pid`, and never probes the default core. A pending live terminal without a PID supplies no process evidence; a missing/finished one cannot match. Machine-qualified addresses supply no local PID.

Shared process inspection chooses the direct tty/session match, else the nearest valid ancestor; see [caller detection](runtime-port.md#identifying-the-caller-terminal). An HC shell inside a herdr pane can carry both identities and still needs no `--runtime`. A stale but live unrelated identity is never adopted. The selected terminal and process start tokens are rechecked before main-session registration. Launch markers constrain placement but do not replace that proof.

Vibestd starts without the builtin runtimes' `CALLER_ENV` values; detectors always use the CLI-supplied values, never the daemon's environment. Both coordinator exec paths preserve the installed runtimes' declared keys. A subagent inherits its online parent's runtime unless a caller or user plugin explicitly chooses otherwise, and a live parent terminal's core proves reachability even when the daemon's default core is offline. S35 proves nested caller detection and subagent inheritance with an isolated core and herdr session.

Setting the plugin up does no I/O (it resolves the socket path from the environment only), because builtin plugins activate before vibestd listens ([plugin-loading.md](plugin-loading.md), architecture.md §7); the notices test checks that the fake core sees no call until one is made. Each call opens its own connection in plain mode (one JSON-RPC message per line). A core is followed from the first call on one of its terminals: one more connection holds `events.subscribe` filtered by `vibest.runtime=hc`; after a loss it is re-made after 0.5 s, then twice as long each time it fails again, at most 30 s apart; after 8 failures in a row (about 90 s) vibestd stops following that core until the next call on one of its terminals. A lost subscription publishes `reset` at once, so a core that never comes back shows as unreachable in the check `reset` starts instead of leaving its sessions running until something calls them. Every snapshot of a core publishes `reset` too, its first one included: the first call on a core after a vibestd restart is often reconcile's own read, and a terminal that exits before the snapshot comes back is already at its shell there, so only the check that `reset` starts sees it. A `missed` notice drops the connection so the next subscription starts from a fresh snapshot.

## Terminals

- A subagent terminal is named from its session title (the explicit `--title`, else the start of its task), slugged to lowercase ASCII and followed by the first four hex characters of its session id: `fix-login-bug-a09e`. An empty slug falls back to the harness name, else `agent`. A new main terminal uses the project directory name plus `-main`, or just `main` when that name has no slug. Names are at most 32 characters, keeping the suffix. If hc refuses a name as taken, `open` tries `-2` through `-9`, truncating the prefix to fit; any other error, or exhausted names, fails the open. Identity stays `<address>@<socket>`; names are only for people. An existing terminal used in place keeps its name: hc has no terminal rename method.
- `open` runs the machine's shell (`keep: true`) and types the argv into it with `terminal.send`, so the shell stays after the program (runtime-boundary rule 4) and `run` types the next program into the same shell. `run` reads the terminal once; when a program still runs in it, it waits for the core's `foreground` event back to the shell (or a fresh snapshot showing it), at most 30 s, without polling. `terminal.send` waits until nobody typed for about 3 s, so each prompt takes at least that long.
- A kept terminal whose program is lost (a signal death, a core crash) gets a shell with the same environment (the runtime-herdr-core test kills the shell with `kill -9` and reads the variable back).
- Exits come from events: `finished`, `removed`, `lost`, and a `foreground` change back to an interactive shell (`sh`, `bash`, `zsh`, `fish`, `dash`, `ksh`, `tcsh`, `nu`, with no script argument) after a program ran. A harness that is itself a shell script would look like a shell; none is.
- `foreground` is the only sign hc 0.1.13 and 0.1.18 give that a program typed into a kept shell ended: the pinned `events.subscribe` description does not list it (created, lost, restarted, keep, finished, removed, status, turn, title, labels, size, doc), `status` and `turn` come only from programs that report OSC 7501, and an isolated core sends `foreground` for `sleep 1` going in and coming back to the shell. So the generated SDK and `gen --check` cannot catch a change to it; `packages/runtime-herdr-core/test/notices.test.ts` replays those lines through a fake core socket on every `pnpm test` (exit, `missed` and a closed subscription to `reset`, `run` waiting for the shell), and the live tests and S33 check it against a real core. A program that ends before the core samples the foreground (`true` gives no event at all) is never seen running, so it gets no exit; every harness runs far longer.
- Compatibility with a core is decided on `hello`, as the official herdr-app does, and a refusal is typed and says which side to update: a newer protocol generation than the pinned one (`HcGenerationMismatch`, update vibest), an older generation (`HcGenerationMismatch`, update herdr-core), a version below the minimum 0.1.13, the oldest release vibest was verified on (`HcCoreTooOld`, update herdr-core), and a method runtime-herdr-core calls (`USED_METHODS` in `packages/effect-herdr-core-sdk/src/hc.ts`) missing from the core's `methods` (`HcMethodsMissing`, update herdr-core). The minimum lives in `packages/effect-herdr-core-sdk/schema/hc-version.json` beside the pin, so the Go desktop can read the same file; versions compare as numbers on major, minor and patch after a leading `hc ` is stripped (0.10 is newer than 0.9). runtime-herdr-core turns each refusal into `blocked` with that message.
- Agent state comes from the harnesses, carried by the terminal: each terminal has one OSC 7501 writer (Pi 1.1.0 and Claude Code natively, Cursor through vibest's hook; see [runtime-port.md](runtime-port.md#terminal-status-ownership)), the core keeps the last report as the terminal's `status`, and runtime-herdr-core offers `state` from `terminal.get` (`working` and `blocked` as they are; `idle`, `done` and `error` as `idle`; no status as `unknown`) and publishes a `state` event on each `status` event. Without it vibestd showed a main agent as `unknown` all along and a subagent as `idle` in its turn. Readiness and turns still come from the integrations directly.
- A text vibestd sends carries no `caller`, and the core types it byte-identical (no `<hc>` tag), proved by the runtime-herdr-core test.

## Labels: herdr-app's conventions

So vibest agents show in herdr-app too (its `docs/labels.md` and the model of spaces, tabs and terminals):

- Every terminal: `vibest.runtime=hc`; a subagent also `vibest.project=<project id>` and `vibest.session=<session id>` from its environment.
- A main agent's terminal: when vibestd records it (`Project.CoordinatorSession`), it calls `present` with `mainSession` and `projectId`, and runtime-herdr-core labels the terminal `vibest.runtime`, `vibest.project`, `vibest.session`, `herdr.space=<project id>` and `herdr.tab=<main session id>`. Other `present` calls change nothing.
- A subagent opened near another terminal (the main agent's, or a `--peer`'s) is started with `parent` set to it, `outlive_parent` (it keeps running when the main agent's program ends) and `no_notify` (the core types no notes into the parent). Without a terminal to start near, `no_parent`. Delivery, parents and results stay vibest's own.

The official herdr-app reads the raw terminal `name` for subagent rows and peek titles (`defaults/mods/agents/main.js`, `defaults/mods/peek/main.js`), and the parent terminal name for the peek source. There is no display-name label. Tab names are different: `defaults/AGENTS.md` documents `tab.rename`, and adoption creates an unnamed tab. They live in the core's `herdr-app` document, which vibest must not write. Main tabs therefore keep the app's name (often `1`); terminal names do not rename tabs.
