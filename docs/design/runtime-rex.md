# The Rex runtime (`rex`)

`packages/runtime-rex` is the builtin runtime plugin `vibest.runtime-rex`, which adds the runtime definition `rex` for Superlogical Rex. It needs a Rex server that speaks API revision 18 or newer (Rex 0.1.0, build 2061). It loads after vibest.runtime-herdr-core and vibest.runtime-herdr, so a terminal that carries herdr or herdr-core variables as well keeps those runtimes; `vibest --runtime rex` names it.

## Reaching the server

The plugin speaks `rex.control.v1` itself: an HTTP upgrade of `GET /api/control` with `Sec-WebSocket-Protocol: rex.control.v1` on the server's Unix socket, then JSON text frames (`hello` and `welcome`, `request` and `response` matched by `id`, pushed `event`s). It does not run the `rex` CLI, which is often not on `PATH`, and does not use the runtime's `WebSocket`, because Bun's `new WebSocket(url, { unix })` ignores `unix` and dials TCP. `protocol.ts` holds the RFC 6455 client framing (masked client frames, 7, 16 and 64 bit lengths, fragments, ping and pong) and the upgrade check, `client.ts` one connection over `effect/socket`.

The socket is `REX_SOCKET`, else `REX_SERVER` when it is a `unix://` URL (percent-decoded, Rex writes `Application%20Support`), else `~/Library/Application Support/rex/server.sock` on macOS and `$XDG_RUNTIME_DIR/rex/server.sock` (`/run/user/<uid>` without it) elsewhere, all read from vibestd's environment. vibest never starts a Rex server. Setting the plugin up does no I/O.

Each call opens its own connection, sends `hello` asking for `api_revision` 18 (without it Rex speaks revision 0 to the connection and ignores `format`'s `max_bytes`, so a scrollback over 1 MiB fails with `too_large`), checks the `welcome`'s `api_server_revision` and calls `session.attach_all` with scope `session`, because Rex refuses session methods (`session.new_window`, `block.event`) on a connection attached to no session. `status` is `offline` when nothing answers, `blocked` naming the revision and "restart Rex Server" when it is below 18 (a Rex update leaves the old server running until Rex restarts), else `online`; every other member then fails with `incompatible`.

## Terminals

- A terminal is a Rex block; its id is `<session id>/<block id>` (`session:…/block:…`), because every block method needs both. Rex sets `REX_SESSION` and `REX_BLOCK` in every block it starts, and nothing else reliably (`REX_SERVER` is not set in local blocks), so those two are the definition's `caller.env`; `caller.target` is the named session or `REX_SESSION`.
- `open` places a block beside `near` with `session.new_split` (horizontal, after, when `split`), else in a new window of `near`'s session or of `target` (a session id or label), else in a new window of the session labelled with the project directory name, creating it with `session.create` when there is none. A placement whose session or anchor is gone falls back to the project session. `focus` is always sent (`input.focus ?? false`), because `session.new_window` focuses by default and `session.new_split` does not. Labels are cut to Rex's 128 characters.
- The flavor is `com.superlogical.terminal.shell` with `shell: "none"`, `close_on_exit: false` and `command` the user's login shell running the launch, as runtime-herdr-core does (`$SHELL -lic '"$@"; exec "$0" -li' $SHELL <launchLine>`, see [runtime-herdr-core.md](runtime-herdr-core.md#terminals)), so the harness is the shell's child and the shell takes the block over when it exits (runtime-boundary rule 4). The shell flavor has no environment option, so the launch environment (without `VIBEST_EXECUTION`) is set by `/usr/bin/env K=V …` in front of it. A launch with no argv runs `$SHELL -li`.
- `send` with `text` is a `block.event` `paste`, never `terminal.write` or `rex send`: `paste` follows the program's DEC mode 2004, so a TUI that turned bracketed paste on gets the whole text between `ESC [200~` and `ESC [201~` with its newlines kept, and a program that did not gets it as typed. `write` types raw bytes, so a multiline `<vibest-agent-message>` would be submitted at its first newline. The text is always submitted with one Enter and any `keys` follow it (`{ text, keys: ["esc"] }` pastes, presses Enter, then Esc), the send contract every runtime shares. `block.event` calls on one connection reach the block in order, and one `send` uses one connection. Keys are `press` and `release` pairs of `key` events: `enter`, `return`, `esc`, `escape`, `tab`, `backspace`, `up`, `down`, `left`, `right` and `ctrl+<letter>`; any other name fails.
- `read` is `format` (`text`, `trim`, `max_bytes` 960 KiB, since a reply may not pass the 1 MiB frame limit) continued with `blob_read` until `eof`, cut to the last `lines` lines.
- `process`: a block whose program exited (`last_exit`) is not running and gives its exit code; a block whose foreground is not an interactive shell (`sh`, `bash`, `zsh`, `fish`, `dash`, `ksh`, `tcsh`, `nu`, with no `script`) is running; at the shell it is running only within 120 s of `run` typing a command, until the foreground leaves the shell. Rex returns only `argv0`, never the other arguments, so a shell running a script is told apart only by `script`. macOS runs the program under `/usr/bin/login`, which is the foreground for a moment at start; it counts as the shell. A block that has no foreground yet (Rex reports `null` while it starts) is running. Rex has no block labels, so the typed time lives in vibestd's memory and a vibestd restart in that window shows the shell as idle. A closed block answers `not_found`.
- `run` waits (at most 30 s, without polling) for the foreground to come back to the shell, then stamps the typed time and pastes `typedLine(launch)` with Enter; the stamp comes first so a program that ends before the Enter returns clears it.
- `close` is `block.close`; a block or session already gone is success. `focus` is `session.focus_block`. `present` sets the block label to `title`, else `agent`, and ignores other keys (Rex has no metadata labels).

## Events and state

The first call on any terminal starts one more connection that holds `session.attach_all` with scope `all`, which includes `block_event`s of sessions that existed before it. Each subscription and each loss publishes `reset`. After a loss it is re-made after 0.5 s, then twice as long each time it fails again, at most 30 s apart, for as long as vibestd runs: Rex is this machine's own server, so quitting it for a while must not end the following. Rex closes a connection that falls 8 MiB of events behind, which is a loss like any other. A connection that was closed fails every later call at once with `unreachable` instead of waiting for an answer.

- `exited`: `block_closed`, `child_exited`, `session_destroyed` (for each block of that session seen so far), and `process_changed` back to the shell after a foreground that was not the shell (`process` marks a block it sees running too, so a reconnect does not lose an exit). The `null` foreground of a starting block and `/usr/bin/login` are not a program: Rex reports `null` and then the launch shell reading its profile, and counting `null` as a program made that first shell look like the harness exiting, so vibestd ended a just-launched session at once. Rex may never report a foreground that lasts only a moment (an isolated server showed no `process_changed` for `sh -c 'sleep 1; exit 3'` started during the shell's rc), so such a program gets no exit event; `process` still answers it. The same holds for a program that prints nothing (`sleep`): Rex pushes no `process_changed` for it, so the shared contract runs with `reportsProgramExit: false`, as runtime-herdr's does.
- `state`: a `program_status_changed` of the root record (no `id`) is OSC 7501 the program wrote; `working` and `blocked` stay, `idle`, `done` and `error` are `idle`. `state(terminal)` reads the same root record with `program_status`, `unknown` when there is none.

## Doctor and other machines

`doctor` reports whether a server answers at the socket, its `rex_version` and its API revision, with the fix to open Rex (or `rex server start`) or restart it. `link` answers this server's `host_id`. A Rex server does not proxy another host's blocks, so `locate` shows none: it names the Rex host in `hosts.list` whose `host_id` matches the peer's link (`rex -S <label>` reaches it), or says that no host here is that machine.

Errors map `not_found`, `session_not_found`, `window_not_found`, `block_not_found` to `not_found`, `busy` and `locked` to `busy`, a lost or unanswered connection to `unreachable`, an old server to `incompatible`, and anything else to `failed`.

## Tests

`packages/runtime-rex/test/protocol.test.ts` checks the framing (every length class fed one byte at a time, fragments with a ping between them, the upgrade answer) and, against a fake socket server that welcomes with revision 11, the `blocked` status and the `incompatible` open. `runtime-rex.test.ts` finds a Rex of revision 18 or newer (`REX_BIN`, else `/Applications/Rex.app` or `/Applications/Rex Beta.app`), is skipped without one, and starts an isolated `rex server run --listen unix:///tmp/vbrex-…/server.sock --state-dir … --restore=false` with an empty `ZDOTDIR` and `REX_RUNTIME_DIR` in the same folder (without it Rex writes `servers/<hash>/` under `~/Library/Application Support/rex` even with `--state-dir`, and `rex server stop` must be given it too to find the server): it runs the shared `runtimeContract`, sends a 20 line `<vibest-agent-message>` to a raw-mode program that turned bracketed paste on and checks it received exactly one paste and one Enter, checks OSC 7501 reports as `state` and `state` events, checks that `split` puts the new block in the near block's window, reads a 1.2 MiB scrollback through `blob_read`, and checks that `{ text, keys }` submits the text. `runtime.test.ts` uses a fake connection: the follower keeps reconnecting under the test clock, and a program `run` types that exits during the Enter leaves the shell idle. `protocol.test.ts` also checks the `hello` asks for revision 18 and that a call after the server's close frame fails at once.

The E2E area `rex` (`e2e/src/scenarios/rex.ts`, capabilities in [docs/features/rex.md](../features/rex.md)) starts the same kind of isolated server per check, with the world's environment and `PI_CODING_AGENT_DIR`, so its blocks and vibestd see one Pi configuration, and runs the built vibest in it: RX1 and RX2 with the fake model, RX3 and RX4 (`--tier agent`) with the user's default Pi provider and model, reached through a copy of the user's Pi settings that loads only the provider packages and links their credential files.
