# Runtime plugins and machines: user stories

Stories for `runtime-port.md`. Each becomes an e2e check (tools/e2e) or a contract-suite case. "You" is the user;
"author" writes a plugin.

## Using a runtime

| ID  | Story                  | Steps                                                                          | Expect                                                                                                                                            |
| --- | ---------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | inside a herdr pane    | `vibest`, then the main Agent delegates a task                                 | The main Agent and the subagent run in herdr, beside each other in the Project's workspace; the result returns; `vibest ls` shows runtime `herdr` |
| R2  | Only tern is installed | `cd shop && vibest` outside any terminal                                       | Refused: no runtime was detected; pass `--runtime tern`. vibest does not pick the only runtime online                                             |
| R3  | An old runtime key     | `"runtime": "rex"` left in vibest.json, then `vibest` inside a herdr pane      | The key warns once and is ignored; the agents run in herdr. `vibest --runtime rex` is what chooses rex                                            |
| R4  | No runtime detected    | `vibest` outside any terminal, with no `--runtime`                             | Refused before anything starts, saying to pass `--runtime`. vibest does not install a runtime                                                     |
| R5  | Step in on any runtime | While a subagent works in rex (or tern), type into its block                   | That round's result still reaches the main Agent once, with what you typed                                                                        |
| R6  | A harness dies early   | A harness exits right after start (broken binary, login prompt it cannot pass) | Within seconds the main Agent gets the terminal's last lines and the exit code, on every runtime; no endless retry                                |
| R7  | Restart vibestd        | Stop vibestd while a subagent works; start it again                            | The subagent kept running in its terminal; vibestd finds it again and its result is delivered                                                     |
| R8  | Two runtimes at once   | A terminal has both hc's and herdr's variables; `vibest`, no `--runtime`       | Without `--runtime`, the terminal it was started in. Both variable sets: hc wins because runtime-herdr-core loads before runtime-herdr            |

## Machines

| ID  | Story                            | Steps                                                                                            | Expect                                                                                                                                                                                                              |
| --- | -------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M1  | Add a machine                    | `vibest machine add cloud ssh://ubuntu@66.80.0.50`                                               | herdr prepares the remote (`--remote-session vibest`), vibest installs its own binary and harness integrations there, prints the harnesses found (`pi`, `cursor-agent`); `vibest machine list` shows `cloud` online |
| M2  | A machine the runtime cannot use | `vibest machine add old ssh://host-with-herdr-0.9.0`                                             | Stops at the status check: "herdr 0.9.0 on old does not support remote API forwarding (needs 0.9.1)"; nothing saved                                                                                                 |
| M3  | Run on a machine by plugin       | A plugin sets `machine: "cloud"` for `reviewer` Agents in `agent.start.before`; ask for a review | The reviewer runs on cloud, in a worktree of the Project's mirror at the pushed commit; its verdict returns to the main Agent on this machine                                                                       |
| M4  | Unpushed work                    | HEAD has local commits not on the remote; a plugin sends an Agent to cloud                       | Refused with "push first: <commit> is not on origin"; nothing starts on cloud                                                                                                                                       |
| M5  | No git remote                    | A Project without a remote; a plugin sends an Agent to cloud                                     | Refused: "the Project has no git remote; it can only run on local"                                                                                                                                                  |
| M6  | Harness missing there            | A plugin sends a Claude Agent to a machine without `claude`                                      | Refused with the machine's harness list; the plugin may pick another harness                                                                                                                                        |
| M7  | Disconnect                       | Cut the network to cloud while its Agent works, restore it later                                 | `vibest ls` shows the Agent `offline`, not failed; after reconnect its result arrives once                                                                                                                          |
| M8  | Work comes back                  | The cloud Agent finishes an implementation                                                       | Its branch is on the remote; the main Agent fetches it and reviews or merges it like a local subagent's                                                                                                             |
| M9  | Remove a machine                 | `vibest machine remove cloud`                                                                    | The entry is gone; nothing on cloud was stopped; Agents still there show `offline`                                                                                                                                  |

## Writing a runtime plugin

| ID  | Story                       | Steps                                                                                                                                                                       | Expect                                                                                                              |
| --- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| P1  | A new product               | The author writes `runtime-foo` with the seven required members, adds it with `context.runtime.transform((editor) => editor.add(definition))`, adds the plugin to `plugins` | `vibest` can run Agents in foo; status, events, exec and presentation fall back as documented                       |
| P2  | Prove it                    | The author runs `runtimeContract(runtime)` from `@vibest/plugin/testing` against a real local foo                                                                           | Every required member passes; each optional member it declares passes; one that is absent is reported as "fallback" |
| P3  | Add a capability later      | The author adds `state` (the product learned to detect agents)                                                                                                              | Core uses it without any change in vibest; `vibest ls` shows the runtime's state                                    |
| P4  | Two plugins, one kind       | Two plugins both add `id: "herdr"`                                                                                                                                          | Load fails naming both plugins                                                                                      |
| P5  | Another machine's terminals | The author implements `link` and `locate`, and the `machine.connect`/`remove` hooks that keep foo's own record of the other machine                                         | `vibest ls` on A shows the terminal of an agent `vibest run --machine b --runtime foo` started on B                 |
| P6  | vibest upgrades the API     | A vibest release changes a required member                                                                                                                                  | The release notes name the change; foo fails to load with a clear message until updated                             |
