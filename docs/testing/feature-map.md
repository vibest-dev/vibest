# Feature map

Every product capability vibest carries from omac, and how it is proven in a real environment: the built
`packages/cli/dist/vibest`, a real herdr, real harness CLIs, a scratch git repository with a local bare `origin`,
the user's own `HOME` (the harnesses' logins) with a temp `VIBEST_HOME` and shadow harness config built from the user's (see
[e2e-plan.md](e2e-plan.md) §1). Fakes do not count.

**Method**

- **script**: deterministic; a `tools/e2e` scenario runs it and checks exit status and output. Pass or fail, no judgment.
- **unit**: deterministic, but no release path reaches it end to end; a named `pnpm test` file proves it.
- **agent**: the outcome needs a real model, an outside event or timing no script controls; an agent follows the steps
  in a real environment and reports each check with its evidence (commands, output, pane text). A check without
  evidence is a fail.
- **slow**: a script check that waits out a product window too long for the gate (`pnpm e2e --tier slow`, nightly).

A skipped check (missing CLI or key) is reported as skipped, never as passed.

This file is the specification, written by hand: each row's Pass when is the authority, and the E2E check with its id
must match it. `pnpm verify` compares ids, not text (tools/verify/README.md): every `script` row needs a gate check
with its id, a `<id>-<case>` check, or a check that covers it; every check id must be a row; a method cell outside the
list above fails it. Rows that are not `script` or `unit` are printed as skipped.

Run the gate's script checks with `pnpm run e2e` (all of tier gate; `--tier slow|agent|all` for the others) or `pnpm run e2e D4 I1` (some) after `pnpm run build`; `pnpm verify`
runs them on a curl and an npm install of this checkout instead, after every other gate. Questions that
only a terminal is asked (`[y/N]`) are answered on a pseudo-terminal. Evidence: `tools/e2e/evidence/<run>/`.
Checks that run a turn run it on a fake model server (`tools/e2e/src/fake-model.ts`: Anthropic Messages for Claude,
OpenAI-compatible for Pi) with shadow harness config, so their prompts and answers are scripted. No gate check runs a real model: I5 and I10 are agent checks (`pnpm e2e --tier agent I5`) on the user's own
Cursor login.

Merged checks keep their ids as cases: naming a covered id runs the check that covers it (D1 covers D2–D4, H1 covers H2
and H3, I7 covers I4, S15 covers S11; T1 is T1-claude and T1-pi). A row proven by checks of other rows names them in
its Pass when, and those checks cover it (D7, D8, G7, R6–R8, S2, S4, S7, S8, S13). I6 is the runner's own check after
every run.

to be a regular file under HOME; an empty Keychains directory is refused. This also keeps T1's daemon
from starting real Cursor behind its hook fixture. H4 puts a sentinel CLI on PATH
and fails if it runs. Direct Cursor commands in the E2E World check the login keychain file too.
When a World changes HOME (including T1), it removes the inherited SSH session indicators; H4 checks
this in a spawned process.

## Integrations (harness adapters)

vibest's plugin for each harness ships in `@vibest/cli` (`harnesses/<harness>`, `VIBEST_HARNESSES`) and is loaded into each
session vibest starts: Pi `-e`, Claude and Cursor `--plugin-dir`. Nothing is installed. I3 and I4 run on a fake model with shadow
config built from the user's (docs/testing/e2e-plan.md §1); I5 uses the user's own Cursor login and config, read only;
the settings the shadows read keep their content (I6). Cursor cannot run on a fake model: `cursor-agent --endpoint` speaks Cursor's own backend protocol, not a
model API a fake can answer, and a real model cannot be held between hook events, so I10 is an agent check on the
user's login.

## Guard (harness adapters)

The pre-tool guard as each harness plugin runs it, proven in a real agent of each harness: I3 (Pi), I9 (Claude), I5
(Cursor, when its real model tries). Pi and Cursor ask vibestd (`Integration.Guard`), which runs the rules and the harness definition's `guardAnswer`.

## Machines

Two vibest homes on one host: A's vibestd dials B through a fake `ssh` first on its `PATH`, which runs the line with
B's environment; agents on both sides run in isolated hc cores on fake models. Design: [multi-machine.md](../design/multi-machine.md).
